# Principal Engineer Failure Matrix

This is the long-term map of failures this repository deliberately injects,
observes, and recovers from. It exists so failure engineering is planned
deliberately across the whole curriculum instead of invented ad hoc, lab by
lab, and so a reader can see the entire failure surface this repository
intends to cover before any single piece of it is built.

**This document defines the roadmap. It does not implement every failure
listed here.** Each row's "Lab / WP" column says whether the failure is
already demonstrated (with a link to where), or which future work package is
expected to own it, or — where no work package has been scoped yet —
`Unscheduled`. Treat `Unscheduled` honestly: it means exactly what it says,
not "coming soon" with an implied date.

## How to read this matrix

For every failure this repository injects — now or in the future — the goal
is always the same seven-part shape, per `CONTRIBUTING.md`'s lab quality
standard:

```text
Expected behavior
Observed behavior
Relevant metrics
Relevant logs
Root cause
Recovery
Production implication
```

The table below is the *index* of failures across the whole curriculum; the
full seven-part treatment for each lives in the lab or doc that actually
implements it, not duplicated here.

## Producer-side failures

| Failure | Observable symptom | Metric / log | Expected Kafka behavior | Data risk | Recovery | Lab / WP |
|---|---|---|---|---|---|---|
| Producer cannot reach any broker | `send()` future fails or times out; client logs repeated metadata-fetch failures | Client-side `NetworkClient` connection-refused/timeout logs; no broker-side signal at all, since the broker never saw the request | Producer retries metadata lookup per `retry.backoff.ms` until `delivery.timeout.ms` is exhausted, then fails the record | Any record accepted into the client's buffer but not yet sent is only as durable as the producer process's memory | Restore broker/network reachability; already demonstrated at the broker level in [`labs/lab-01-first-kafka-cluster`](../../labs/lab-01-first-kafka-cluster/README.md#failure-kafka-broker-unavailable) | Demonstrated (Lab 01, broker-unavailable). Deeper producer-client-side framing: WP-03/Client resilience (Unscheduled beyond WP-03's basics) |
| Broker appends the record, but the ACK response is lost before the producer sees it | Producer believes the send failed or timed out and retries; the record may already be durably appended | Broker-side: the record is visible in the log/offset even though the producer logged a failure; producer-side: a retry log line | Without idempotence, retrying an unacknowledged-but-actually-successful send appends a duplicate; with `enable.idempotence=true`, the broker's producer-ID/sequence-number tracking detects and drops the duplicate | Duplicate application-visible records if idempotence is off; none if it's on (for this specific failure shape) | Retry is automatic; verifying no duplicate landed is the actual exercise | WP-09 (transactions & exactly-once semantics — producer idempotence) |
| Broker dies before a record is replicated to any follower | In-flight produce requests to that broker fail; a new leader (once elected) does not have the record | Controller/leader-election logs; consumer sees the topic's log end offset *not* include the lost record | With `acks=all` and `min.insync.replicas` satisfied before the crash, the record should already be safely replicated; if it crashed before replication completed, an unreplicated record is lost from the failed broker's perspective — whether it's lost from the cluster's perspective depends on whether any acknowledgment was actually sent | Real — this is precisely why `acks` and `min.insync.replicas` exist together | Broker rejoins as a follower and catches up; the acknowledgment contract (or lack of one) determines whether "recovery" also means "no data was lost" | WP-07 (replication, ISR & broker failure) |
| Leader dies (already elected, cluster stable) | Producers to affected partitions see leader-not-available errors briefly | Controller logs a leader-election event; `Leader:` field in `kafka-topics --describe` changes | A new leader is elected from the ISR; producers refresh metadata and resume against the new leader | Depends entirely on whether `unclean.leader.election.enable` is false (default) and whether the new leader was fully in-sync | Automatic once metadata refreshes; the interesting question is *how much* was at risk during the gap | WP-07 |
| ISR shrinks below `min.insync.replicas` | Producers using `acks=all` start receiving `NotEnoughReplicasException` | `UnderReplicatedPartitions` broker metric rises; ISR shrink logged on the leader | Kafka refuses to accept `acks=all` writes rather than accept them with insufficient durability | None to *existing* data; new writes are correctly rejected instead of silently under-protected | Restore the missing replica(s) to the ISR | WP-07 |
| Controller (KRaft quorum leader) dies, in a multi-voter quorum | Metadata operations (topic creation, leadership changes) stall until a new controller is elected | `kafka-metadata-quorum.sh describe --status` shows a leader-election event | The remaining voters elect a new controller leader via Raft, as long as a majority of voters are still reachable | None to existing topic data; risk is to *new* metadata operations during the gap, and total cluster metadata unavailability if a majority of voters is lost | Restore quorum majority | WP-08 (KRaft controller quorum & failure) |

## Consumer-side failures

| Failure | Observable symptom | Metric / log | Expected Kafka behavior | Data risk | Recovery | Lab / WP |
|---|---|---|---|---|---|---|
| Consumer crashes before committing an offset it already processed | On restart (or after rebalance), the same record is fetched and processed again | Consumer-group `CURRENT-OFFSET` unchanged despite the record having been handled once already | This is at-least-once processing working exactly as designed — see [the mental model's fetch/processing/commit distinction](../architecture/KAFKA_MENTAL_MODEL.md#10-fetch-position-processing-side-effects-and-committed-offset-are-five-different-things) | A duplicate business side effect, unless the consumer is idempotent | None needed at the Kafka level; the application must be built to tolerate this | Demonstrated conceptually in [`KAFKA_MENTAL_MODEL.md`](../architecture/KAFKA_MENTAL_MODEL.md); hands-on: introduced in WP-06 (`lab-05`, a single `eventId` check against a durable store), full production treatment in WP-13 (idempotent-consumer topic; see the curriculum map) |
| Consumer commits an offset before the side effect it represents is guaranteed to have completed, then crashes | The record's business effect never happens, and no future redelivery will retry it, because the offset says "done" | Nothing broker-side distinguishes this from a normal commit — the gap is entirely inside the consumer's own logic | This is at-most-once processing — Kafka did exactly what it was told | A silently skipped business operation | None at the Kafka level; requires reordering the application's commit-vs-processing logic | Demonstrated conceptually in [`KAFKA_MENTAL_MODEL.md`](../architecture/KAFKA_MENTAL_MODEL.md) |
| Consumer processing takes longer than the configured poll/session liveness allowance (`max.poll.interval.ms` is the client-side knob most directly associated with this, but the exact enforcement mechanism is protocol-dependent — see "Expected Kafka behavior") | Partition ownership may move away from the slow consumer while its earlier processing is still in flight | Coordinator/broker logs a group-membership change or session-timeout event; which timeout config is actually enforced (`session.timeout.ms` client-side under the classic group protocol, or the broker-side `group.consumer.session.timeout.ms` under the newer "consumer" group protocol / KIP-848) depends on `group.protocol` | This is an architectural principle, not one fixed sequence: poll → processing runs long → the consumer exceeds its poll/session liveness contract → partition ownership *may* be lost and reassigned, according to whichever consumer-group protocol and configuration is active → another consumer may then process that partition → the original consumer's earlier processing may still have external work in flight → commit, reprocessing, and duplicate-side-effect risk follows. Do not treat exceeding `max.poll.interval.ms` as equivalent to a heartbeat failure — under the classic protocol, a background heartbeat thread can keep succeeding independently of a blocked `poll()`, and static membership (a non-null `group.instance.id`) delays reassignment until session-timeout expiry rather than reassigning immediately. Exact mechanics vary by Kafka/client version, active group protocol, and configuration — see the deferral to WP-05 below rather than treating this cell as a spec | If the original consumer attempts to commit after losing ownership, that commit is at risk of being fenced by the group's generation/epoch tracking and can fail outright (for example, a `CommitFailedException` under the classic protocol) rather than silently succeeding — but a failed commit does not undo any external, non-Kafka side effect the original consumer already performed, so duplicate or overlapping processing risk remains regardless of whether the commit itself succeeds or is rejected | Reduce processing time per `poll()` batch, increase the poll/session liveness allowance deliberately (a trade-off, not a fix), or hand off long work to a separate thread while `poll()` keeps returning promptly | WP-05 (consumer groups and rebalancing) — exact mechanics are to be experimentally verified there against this repository's pinned Kafka/client version (`apache/kafka:4.3.1`, see `platform/kafka/docker-compose.yml`), covering both group protocols where they materially differ: normal poll → slow processing → liveness allowance exceeded → ownership transition → rebalance → commit attempt → duplicate/reprocessing behavior → recovery. Not implemented yet |
| Rebalance occurs mid-processing (not necessarily due to a timeout — e.g., another member joins or leaves normally) | Partition ownership moves while a consumer is partway through a batch | Rebalance-listener callbacks fire (`onPartitionsRevoked`/`onPartitionsAssigned`) | Correct behavior depends entirely on whether the application commits (or otherwise checkpoints) in `onPartitionsRevoked` before losing the partition | Duplicate or skipped processing around the rebalance boundary if revocation isn't handled carefully | Implement `onPartitionsRevoked` to commit/checkpoint before giving up ownership | WP-05 |
| Duplicate event delivered (any cause above) | Same business event processed more than once | Depends on cause — see the two consumer rows above | Kafka's at-least-once default explicitly allows this; only idempotent producers + `read_committed` + consumer-side idempotency together approach "effectively once" | Duplicate business side effects unless guarded against | Idempotency key / processed-event table / unique constraint at the consumer's side-effect boundary | Idempotent-consumer topic — introductory version in WP-06, full dedicated-lab treatment in WP-13 (conceptually anchored after WP-12) |
| Poison event (a record the consumer cannot successfully process, ever) | Consumer repeatedly fails on the same offset and either blocks the partition or loop-retries forever | Consumer error logs show the same offset repeatedly; lag on that partition stops decreasing | Kafka has no concept of a poison event — it will redeliver the same record indefinitely if the consumer never advances past it | A stuck partition blocks every record behind it in that partition, not just the bad one | A dead-letter topic / retry-topic strategy that lets the consumer commit past the bad record after diverting it | WP-13 (retry, DLQ & idempotency) |
| Incompatible schema encountered | Deserialization exception on consume | Consumer error logs show a deserialization/schema-compatibility failure | Kafka itself enforces no schema at all — this is entirely a serialization-layer failure, not a broker-level one | Same "stuck partition" risk as a poison event, unless handled the same way | Schema compatibility policy enforced at write time (so this can't happen), plus a DLQ path for when it does anyway | WP-10 (schema evolution) |
| Consumer lag explosion (sustained, not transient) | `LAG` in `kafka-consumer-groups --describe` grows without bound | Consumer-lag metric trending up with no recovery; broker-side metrics typically normal | Kafka has no built-in backpressure toward producers based on consumer lag — production continues regardless of how far behind consumers fall, up to retention limits | Once lag exceeds retention, unconsumed records are deleted — an actual data-loss path for that consumer group, not just a delay | Scale consumer parallelism (bounded by partition count), fix a slow per-record dependency, or accept the trade-off deliberately | WP-16 (observability) surfaces this; root-causing it draws on WP-04 (partitioning) and WP-05 |

## Cluster and storage failures

| Failure | Observable symptom | Metric / log | Expected Kafka behavior | Data risk | Recovery | Lab / WP |
|---|---|---|---|---|---|---|
| Hot partition (severe key skew) | One partition's leader broker shows much higher CPU/disk/network load than its peers | Per-partition throughput metrics uneven; one broker's resource metrics elevated relative to others | Kafka does not rebalance load based on traffic skew on its own — a hot partition stays hot until the key distribution or partition count changes | No data-loss risk directly, but a throughput/latency ceiling for that key's traffic, and potential broker-wide resource contention affecting *other* partitions on the same broker | Partition-key redesign, increased partition count (with its own ordering trade-offs — see Partition Lifecycle Engineering below), or explicit load-aware placement | WP-04 (partitioning); revisited under Cluster Rebalancing, folded into WP-20 (Planned) |
| Disk fills on a broker | Broker refuses writes to affected partitions; may shut down disk-online state for that log directory | `kafka.log.LogManager` / disk-related error logs; disk-usage metric at or near capacity | Kafka does not preemptively throttle writes as disk fills — behavior is a hard failure at or near capacity, not a graceful slowdown | High — a broker in this state can affect every partition it hosts, not just one | Free or expand storage, or adjust retention; simulate safely in a lab via retention/size limits rather than filling a real disk | WP-19 (failure engineering & production simulation), simulated safely rather than via literal disk exhaustion |
| Broker resource imbalance after adding/removing brokers | New brokers sit idle while existing brokers remain fully loaded | Per-broker resource metrics uneven post-change | Kafka does **not** automatically move existing partition replicas onto new brokers — partition assignment is decided at creation/reassignment time, not continuously rebalanced | No data-loss risk; a capacity-planning and cost-efficiency problem, not a correctness one | Explicit partition reassignment (manually or via Cruise Control) | Cluster Rebalancing & Cruise Control, folded into WP-20 (Planned) |
| Network latency/partition between brokers | Replication lag rises; ISR may shrink if followers fall behind fetch-lag thresholds | `MaxFollowerLag`/ISR-shrink logs | Followers that fall too far behind are removed from the ISR to protect the durability guarantee `acks=all` depends on | Durability-tier risk, not immediate data loss — but see the ISR-shrink row above for what happens if it shrinks below `min.insync.replicas` | Restore network path; affected replicas rejoin ISR once caught up | WP-07 |
| Multi-cluster / region loss | An entire cluster or region becomes unreachable | Cross-cluster replication lag/alerting (implementation-specific) | Entirely dependent on the DR architecture chosen (active/passive vs. active/active) — Kafka has no built-in cross-cluster failover | RPO/RTO-dependent, and must be defined *before* the failure, not discovered during it | Failover per the DR runbook, followed by a deliberate, tested failback | Multi-Cluster & Disaster Recovery, folded into WP-20 (Planned) |

## Integration and processing failures

| Failure | Observable symptom | Metric / log | Expected Kafka behavior | Data risk | Recovery | Lab / WP |
|---|---|---|---|---|---|---|
| Kafka Connect task failure | A connector's task stops processing; Connect marks the task `FAILED` | Connect worker REST API / logs show task state and stack trace | Kafka Connect does not automatically retry a permanently failed task past its configured retry policy | Source connectors: upstream changes may not be captured until restarted; sink connectors: downstream writes stop | Restart the task (manually or via `errors.tolerance`/DLQ configuration) after fixing the root cause | WP-11 (Kafka Connect & CDC) |
| Source database unavailable during CDC | Debezium's connector task fails or blocks | Connect task state `FAILED`; Debezium connector logs show the connection failure | Debezium resumes from its last committed offset (in the database's WAL/log position, not just a Kafka offset) once the source database is reachable again — assuming that WAL position hasn't been reclaimed in the meantime | If the source database's WAL/replication slot retention is exceeded during the outage, CDC can lose the ability to resume cleanly and may require a new snapshot | Restore database availability before WAL retention is exceeded; monitor replication-slot lag as a leading indicator | WP-11 (Debezium CDC, within Kafka Connect & CDC) |
| Kafka Streams process dies | The Streams application instance stops; its partitions' tasks are reassigned to remaining instances (if any) | Streams application logs show task migration; consumer-group rebalance for the Streams app's internal consumer | Kafka Streams rebuilds any local state for migrated tasks from the task's changelog topic before resuming processing | Processing pause proportional to changelog-based state-restoration time, not data loss (assuming changelog topics are intact) | Restart the failed instance, or let remaining instances absorb its tasks; restoration time is the thing to actually measure | Demonstrated ([`lab-13-kafka-streams`](../../labs/lab-13-kafka-streams/README.md#experiment-4--a-streams-process-dies), WP-14) |
| Kafka Streams state restoration takes a long time | Extended processing pause after a task migrates or an instance restarts | Streams restoration-related metrics/logs (restore progress) | Expected and proportional to changelog size — this is the direct cost of Streams' local-state, changelog-backed design | Availability/latency risk, not data-loss risk | Standby replicas (where used) reduce restoration time by keeping warm copies elsewhere; otherwise, restoration simply takes as long as it takes | Demonstrated ([`lab-13-kafka-streams`](../../labs/lab-13-kafka-streams/README.md#experiment-5--standby-replicas-shrink-restoration-time), WP-14) |

## Notes for every future entry added to this matrix

- A failure only belongs in the `Demonstrated` state once a real lab actually
  injects and recovers from it — matching this repository's rule against
  fake production claims. Everything else stays honestly `Unscheduled` or
  pointed at a specific future WP.
- Every entry must have a recovery path. A failure with no recovery step is
  an incomplete entry, per `CONTRIBUTING.md`'s "every failure lab needs
  recovery instructions" rule.
- Metrics and log lines referenced here should be re-verified against the
  actual pinned Kafka version's output when the corresponding lab is built —
  this matrix describes expected signal *categories*, not exact, tested log
  strings, except where a row explicitly links to a lab that has already
  captured real output.
